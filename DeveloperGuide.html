Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delc c/1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, ClientListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Client objects from the model.

Command feedback states

CommandResult carries a FeedbackType (NEUTRAL, SUCCESS, or ERROR) alongside its unchanged feedback string and help/exit flags. Existing constructors default to SUCCESS; overloads accept an explicit type. Equality, hashing, and the string representation include the type. find, findp, list, help, and exit return NEUTRAL; commands that change records use SUCCESS.

MainWindow#executeCommand(...) passes the result's message and type to ResultDisplay#setFeedbackToUser(String, FeedbackType). It catches ParseException and CommandException, displays ERROR, and rethrows the exception so CommandBox retains failed input. Storage failures follow the same error path: for executed commands, LogicManager saves before returning the result, so a failed save never displays that result as a success. The existing storage behavior still applies: a save failure may occur after the in-memory model has changed; feedback does not roll it back.

ResultDisplay owns presentation. It maps the type to an Info, Success, or Error label and one of the mutually exclusive feedback-neutral, feedback-success, and feedback-error CSS classes. Each update removes previous state classes, preserves the original message, and resets the caret and scroll offsets to the beginning. A read-only, wrapping TextArea provides selection and vertical scrolling for long feedback. The one-argument setter defaults to SUCCESS for compatibility. Startup guidance is NEUTRAL. Feedback arguments are checked for null before changing any visible state.

CommandBox keeps input correction separate from the last outcome: editing clears its own error style without clearing the feedback, and successful execution clears the input. Repeated failures do not add duplicate input error classes. Its executor must be non-null at construction.

Empty list and card states

Logic#getClientList() exposes the model's unmodifiable observable list of all stored clients. MainWindow passes this list and Logic#getFilteredClientList() to ClientListPanel. The ListView displays the filtered list and uses its placeholder only when that list is empty. The placeholder's text is bound to whether the stored list is empty: no stored clients takes precedence over no matches. Its width is bounded by the list width, clamped at zero during initial layout, so its text can wrap. Both list arguments must be non-null; the UI never changes their contents directly.

ClientCard rejects a null client and renders missing pets and active appointments as subdued, wrapping labels. A pet gets one empty-note label only when its entire notes map is empty; partial notes keep their existing labels and safety markers. emptyHistory is visible and managed only while history is empty, so it reserves no space after the first completed session. Populated history displays up to three recent session snapshots, while all records remain in the model and storage. Model updates replace immutable clients, causing list cells to rebuild their cards and recompute empty sections. No command syntax or storage schema changes are required.

Tests use the shared JavaFxTestUtil toolkit and run new UI scenarios on the JavaFX application thread. ResultDisplayTest checks all state transitions, rejected null feedback, and long-message scrolling; FeedbackUiIntegrationTest covers parsing, execution and saving failures plus correction behavior. EmptyStateFixtures supplies empty and populated sections, including partial/full notes and history. ClientCardEmptyStateTest, ClientListPanelTest, and EmptyStateUiIntegrationTest verify placeholders, reused cells, filtering, and transitions through real commands. LogicManagerTest verifies that the stored list stays observable across changes and cannot be modified through the Logic API.

Appointment presentation and refresh

ClientListPanel displays each client through a ClientCard in the existing ListView. ClientCard sorts Client#getAppointments() by calendar date and then start time, earliest first, when rendering. The stored list remains in insertion order. Its private appointment formatter reads the date, start time, optional end time, recorded linked names and booking details directly from Appointment. A row such as Appointment: 12-12-2026 14:00–15:30 · Milo, Luna (Full groom) omits the end-time range when no end time exists and omits parentheses for blank details.

The formatter uses Appointment#getPetNames() in recorded order, rather than looking up the client's current pets. An empty collection displays No pets linked; it never implies all the client's pets. Unresolved names in existing records remain visible, so displaying a card does not lose booking information.

Pet summaries, appointment rows and pet notes share wrapping-label configuration. The FXML containers allow content to shrink horizontally, while labels keep their computed preferred height. Each list cell binds its card's preferred and maximum widths to its available width after insets, allowing wrapping and variable row heights. Replacing or clearing a cell unbinds its previous card.

Model updates replace immutable clients through Model#setClient(...), which replaces an element in the observable client list. The displayed list then updates its cells and recreates affected cards. Client#withPetReplaced(...) updates active appointment names after a rename, and Client#withoutPet(...) removes deleted pets from active links. Removing the final link displays No pets linked on the next card update. Presentation adds no per-pet listeners or separate refresh mechanism.

Rendering tests cover linked/unlinked rows with optional end times, stored details, ordered names and unresolved names. Layout tests exercise wrapping at narrow widths; list tests verify model-driven refresh and binding cleanup during cell reuse. UI assertions run on the JavaFX application thread.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an PawPalsParser object, which in turn creates a parser that matches the command (e.g., DeleteClientCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteClientCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a client).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Model component

API : Model.java

The Model component,

  • stores the PawPals data i.e., all Client objects (which are contained in a UniqueClientList object). Each Client also holds its own pets, active appointments and completed-session history, described in Pets and appointments and Completed-session history.
  • stores the Client objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Client> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in PawPals, and each Client references tags from that list. This lets PawPals maintain one Tag object per unique tag instead of each Client holding its own Tag objects.

Pets and appointments

The class diagram below shows how a Client's pets and appointments are modelled.

  • A Pet has a PetName, Species and Breed, and up to three PetNotes: at most one for each NoteType (PREF preference, SENS sensitivity, TEMP temperament). Sensitivity and temperament notes count as safety information.
  • An Appointment has an AppointmentDate, a start AppointmentTime, an optional end AppointmentTime and free-text details. Within a client, an appointment is identified by its date and start time.
  • An Appointment links to the pets it covers by PetName, not by Pet object. Pet names are unique within a client (ignoring case), so a name is enough to find the pet, and Client#getPetsFor(Appointment) returns the linked Pet objects.
  • Like Client, these classes are immutable. Changes such as Pet#withNote(...) or Client#withPetReplaced(...) return a new object.

AppointmentCommandParser accepts repeated optional pn/ fields using the shared PREFIX_PET_NAME and ParserUtil#parsePetName(...). Required client/date/start parsing still uses ParserUtil#parseAppointmentTarget(...). At execution, AppointmentCommand resolves every requested name through the displayed client's Client#getPet(...), then stores the recorded names once in first-reference order. This reuses existing case-insensitive pet identity rules and preserves the appointment's other fields. Missing pets reject the command before any model update. The resolved appointment uses the same global Model conflict check as client-only bookings; omitting pn/ does not infer participating pets.

appt accepts past, current and future starts. Its injected clock is used only to add an informational note to success feedback for past starts. Past appointments use the same pet validation and active-booking conflict checks as future appointments, and remain active until cancelled or recorded with done.

Design consideration: how an appointment refers to its pets

  • Alternative 1 (current choice): store the pet's name.
    • Pros: Pet objects are immutable, so editing a pet replaces the object; a name stays valid across edits. The data file stays simple, and older files without linked pets still load.
    • Cons: the links must be updated when a pet is renamed or deleted. Client#withPetReplaced(...) and Client#withoutPet(...) do this, so commands never have to.
  • Alternative 2: store a reference to the Pet object.
    • Pros: no lookup by name.
    • Cons: after a pet is edited, appointments would still point to the old Pet object, and saving the reference to the data file would need an ID scheme.

Global appointment conflicts

Commands call Model#findAppointmentConflict(candidate) through the Model facade. ModelManager delegates the check to AppointmentConflictChecker, which returns either the first conflicting active appointment and its owning client, or an empty optional.

The activity diagram below shows the global conflict-checking workflow. The check runs before Model#setClient(...), so rejected bookings leave the data and current filter unchanged.

Commands call Model#findAppointmentConflict(candidate) to check active bookings through the Model facade. ModelManager delegates to AppointmentConflictChecker, which scans the full client list's active appointments using Appointment#overlaps(...). It returns the first conflict with its owning client, or an empty optional. It ignores the current UI filter and completed-session history. appt checks this before replacing a client, so rejected bookings leave data and the filter unchanged. Messages#formatAppointmentConflict(...) supplies feedback including the owner and conflicting slot.

The overload Model#findAppointmentConflict(candidate, originalClient, originalAppointment) supports editappt. It excludes only the original owner's booking identified by date and start time, while checking all other bookings. The editing command must validate its target, run this check before mutation, then use Client#withAppointmentReplaced(...) and one model update. A client-only appointment and appointments for different pets follow the same overlap rules.

Appointment rescheduling

PawPalsParser dispatches editappt to EditAppointmentCommandParser. The parser reuses ParserUtil#parseAppointmentTarget(...) for required c/, d/ and t/, and the existing validated date/time types for optional nd/, ns/ and nonempty ne/. Empty ne/ sets the descriptor's clearEnd flag; omitted ne/ preserves duration. Tokenization trims whitespace, so whitespace-only ne/ also clears. It rejects duplicate prefixes, non-empty preambles, missing target fields and invalid values. The immutable EditAppointmentDescriptor requires at least one replacement value or clearEnd, including when a command is constructed directly. Supplying both an explicit end and clearEnd is rejected. The three-argument constructor defaults clearEnd to false. End-time ordering and duration checks belong to execution because omitted values depend on the original appointment.

EditAppointmentCommand performs these steps:

  1. Resolve the client from the displayed list and look up its active appointment by original date/start.
  2. Construct a replacement using the supplied values and the original details and ordered pet links. When clearEnd is true, use no end time and skip duration preservation. Otherwise, without a supplied end, retain a missing end or preserve the existing duration. Compute the proposed end in minutes and reject an end at or after midnight before converting it to LocalTime, avoiding wraparound. Exactly 23:59 is valid. A supplied ne/HH:mm overrides this calculation.
  3. Validate the end through Appointment's constructor. Past, current and future resulting starts are accepted, including for end-only edits and unchanged starts.
  4. Check all active bookings with Model#findAppointmentConflict(candidate, client, original). Only the original owner's original date/start is excluded; the filter and history do not limit the scan.
  5. Use Client#withAppointmentReplaced(...), then call Model#setClient(...) exactly once. This preserves appointment position, other client data, history and the current predicate. Validation failures occur before mutation. LogicManager saves the updated model through the existing storage path.

Success feedback identifies the owner, original and resulting starts, and the resulting end when present. If the resulting start is earlier than LocalDateTime.now(clock), it appends the same past-appointment guidance as appt. The clock uses the system's local zone by default; tests inject fixed clocks to cover past/current/future boundaries and time zones. The appointment remains active until completed or cancelled. The observable list replacement updates the card immediately. The current card format displays the date, start, optional end time, recorded pet names and any nonblank booking details. End-only edits update the displayed range as well as feedback and saved data. No storage schema change is needed. Save errors retain the application's existing behavior: memory may already contain the replacement when writing the file fails.

Tests are separated by responsibility: EditAppointmentCommandTest uses a model stub for validation, duration boundaries and update/delegation checks; EditAppointmentCommandIntegrationTest uses the real model for filtering, conflict exclusion and preservation. EditAppointmentCommandParserTest covers syntax independently. EditAppointmentPersistenceIntegrationTest exercises dispatch, saving and reloading; EditAppointmentUiIntegrationTest drives the actual command box, feedback display and list controls. UI tests share a JavaFX toolkit via JavaFxTestUtil because it cannot restart after Platform.exit() in the same test worker. Full checks run with gradlew check coverage.

Completed-session history

History is stored under its owning Client as an immutable List<CompletedSession>, separate from the active appointments returned by Client#getAppointments(). The done command uses this model/storage foundation; history presentation is handled by the UI.

DoneCommandParser reuses ParserUtil#parseAppointmentTarget(...) for client/date/start parsing and the existing PREFIX_NOTE for required nt/ session notes. It uses ArgumentTokenizer#tokenizeWithTrailingText(...) to preserve prefix-like note text when a single nt/ follows all three target fields. Other field orders use normal tokenization, and duplicate prefixes before the notes or a repeated nt/ are still rejected. SessionNotes handles trimming and length validation. PawPalsParser dispatches done to this parser.

DoneCommand resolves the target against the displayed client list, checks active appointments first, and uses history only to distinguish an already completed slot from a missing booking. It delegates completion eligibility and snapshot creation to Client#completeAppointment(...), using an injectable clock, then applies the replacement with exactly one Model#setClient(...) call. This keeps completion and active removal together without changing the filter. Future starts become a command error before the model is updated. Success feedback identifies the client, slot, recorded pets and session notes.

Each CompletedSession retains:

  • An immutable Appointment snapshot: date, start time, optional end time, booking details and linked pet names.
  • Required SessionNotes: 1–200 characters after trimming leading and trailing spaces. These describe the visit and do not replace booking details or a pet's standing preference/safety notes.
  • loggedAt, an Instant recording when the session was logged. It does not claim to be the actual finish time.

Completion and identity rules

  • Client#completeAppointment(date, time, notes, clock) looks up the active appointment by date and start time. It returns a replacement client with that appointment removed and one history record added. The caller applies the result with one Model#setClient(...) call, preserving the current filter.
  • Completion is allowed at or after the scheduled start, interpreted in the supplied clock's local zone. It may occur before the scheduled end, or much later than the visit. The logging instant is read once from that same clock. A future start or missing active appointment leaves the original client unchanged.
  • Repeating completion without another active appointment fails. hasCompletedAppointment(date, time) lets DoneCommand distinguish an already logged slot from one that never existed. Always look for an active appointment first; an old history record must not block a new booking at that slot.
  • History has no date/start-time uniqueness constraint and never reserves time. Booking and conflict checks use active appointments only; appt also accepts past and current starts.
  • An appointment without linked pets remains a client-only session. Current pets are not inferred as participants. A visit covering several pets creates one record with all its recorded pet names.

Preservation, display and storage rules

  • Pet rename/deletion updates active appointment links but preserves all historical pet names. Render history from its snapshot rather than resolving those names through Client#getPetsFor(...). Names are historical labels, not stable identifiers for automatic per-pet matching across renames.
  • All client-copy operations and contact edits preserve history. This includes adding pets/appointments, changing pet notes, rescheduling and removing appointments. Deleting a client removes its history; clear removes every client's history. There is no individual history edit/delete operation in this scope.
  • Client#getHistory() returns all records, sorted by appointment date and start time descending, then logging instant descending. Equal keys retain their insertion order. A UI preview of three records must not discard older stored sessions; the UI applies its limit only when rendering.
  • JsonAdaptedCompletedSession stores the appointment snapshot, notes and an ISO-8601 logging instant. JsonAdaptedClient stores these records in an optional history array. Missing or null history in older files loads as empty history; empty history is omitted when saving.
  • Stored records validate required fields and appointment/note/timestamp formats. Invalid entries reject the file rather than silently dropping history. Loading does not reapply completion eligibility against the current clock, or require historical pets to remain in the client's current pet list.

Example entry in a client's history array:

{
  "appointment": {
    "date": "20-10-2026",
    "time": "14:00",
    "endTime": "15:00",
    "details": "Call on arrival",
    "pets": ["Milo"]
  },
  "notes": "Teddy cut, short ears",
  "loggedAt": "2026-10-21T06:30:00Z"
}

The single-client update guarantees that active removal and history creation happen together in memory. Persistence still uses the existing LogicManager save pipeline; this model operation does not introduce disk transactions or rollback on save errors.

Completed-session rendering

ClientCard adds a History section beneath active appointments. Its private HISTORY_DISPLAY_LIMIT is three: it consumes Client#getHistory() in the supplied order using stream().limit(...), leaving the complete immutable list and storage unchanged. Each session is a pair of wrapping labels: snapshot date/start/optional end and recorded pet names, followed by Notes: .... An empty pet set renders as No pets linked. Booking details and loggedAt remain stored but are not displayed.

The shared appointment-summary formatter reads CompletedSession#getAppointment() directly. It never resolves historical names against current pets, so later rename/deletion cannot rewrite what the completed visit displays. All labels wrap and grow vertically at narrow widths. An empty history shows No completed sessions beneath the History heading and has no session rows. The placeholder is hidden and unmanaged when completed sessions are present.

The existing JavaFX observable-list mechanism refreshes the card after DoneCommand applies its single Model#setClient(...) replacement. The UI displays active removal and history creation from that same replacement without resetting the filter or adding a command-to-UI dependency.

Rendering tests cover zero through four sessions, recorded names, absent end times/pet links, ordering ties, client isolation and long wrapping notes. The command-box integration test checks immediate refresh under a filter, retention of four records after JSON reload, and subsequent pet rename/deletion without changes to displayed historical names.

Storage component

API : Storage.java

The Storage component,

  • can save both PawPals data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonPawPalsStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)
  • stores each client's pets, active appointments and completed sessions inside that client's JSON object. A pet's notes are saved in its notes object, keyed by note type, e.g. "notes": {"pref": "Teddy cut", "temp": "Nervous around dryers"}.
  • treats every field added after v1.3 (pet notes, an appointment's end time and linked pets, and session history) as optional, so data files saved by older versions still load.

LogicManager#execute(...) saves after a command returns successfully, including read-only commands such as list, find and help. A clear request only sets a private, session-local confirmation flag and returns neutral feedback. While pending, Logic handles the next input as a confirmation response before normal parsing. Only y/Y (after trimming whitespace) executes ClearCommand through the shared execution-and-save path; n/N cancels without saving. Invalid responses throw ParseException and retain the flag. The flag resets before confirmed execution, including when saving fails. The UI and model do not own confirmation state. Parsing and command-execution failures bypass saving. A save failure becomes a CommandException; model changes have already happened and are not rolled back. FileUtil#writeToFile(...) uses Files.write(...) directly, so writes are not atomic and an I/O failure does not guarantee an unchanged file. MainApp fixes the data path at data/pawpals.json relative to the process working directory.

Corrupted-data recovery

When JsonPawPalsStorage cannot convert data/pawpals.json into a valid PawPals model, MainApp must not immediately treat the empty recovery model as ordinary data. The recovery flow is:

  1. JsonPawPalsStorage.readPawPals() throws DataLoadingException after JSON or model validation fails.
  2. MainApp.initModelManager(...) asks the Storage component to create a backup before constructing an empty PawPals model. The backup is created by JsonPawPalsStorage.backupCorruptedData() using a unique temporary name based on the original file, such as pawpals.json.corrupt-12345.bak. The original rejected file is never used as the backup destination and is not overwritten during this step.
  3. DataRecoveryInfo carries the original path, the optional backup path, and the loading error from MainApp to UiManager.
  4. After the main window is created, UiManager shows a modal warning before the command box can be used. It explains that the application is using an empty client list and identifies the backup file when one was created.
  5. The user must choose Continue or Exit. Continuing permits normal commands and therefore permits the existing auto-save pipeline to replace the rejected file with the user's new empty-data state. Exiting closes the application before any command can trigger an auto-save, preserving the rejected file and its backup.

If backup creation fails, the warning explicitly says that no backup was created. The application still requires the same confirmation before continuing, so the user is aware that the rejected file cannot be recovered automatically. Missing data files are not considered corruption: they continue to load sample data without a recovery warning. Valid files, including valid files containing zero clients, also follow the normal startup path.

The storage tests verify that backups preserve the exact rejected bytes, that repeated recovery attempts receive different backup paths, and that the original file remains unchanged. Manual testing should verify both confirmation choices: Exit must leave the rejected file unchanged, while Continue followed by a successful command may replace it with the current model.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Deleting a pet note: delnote

delnote c/CLIENT_INDEX pn/PET_NAME ty/TYPE removes one note from one of a client's pets, keeping the pet's other notes. note adds or replaces a note, and its nt/ is required, so delnote is the only way to remove one.

The sequence diagram below shows how delnote c/1 pn/Milo ty/temp is executed. Parsing works as in the delc example in the Logic component, so it is shown as a ref frame.

  1. DeleteNoteCommandParser parses the client index, pet name and note type into d:DeleteNoteCommand. The note type is parsed by ParserUtil#parseNoteType(...), which note also uses.
  2. d gets the displayed client list from the Model, picks client c at the given index, and looks up the pet by name, ignoring case.
  3. d checks that the pet has a note of that type, then builds the updated objects. Pet and Client are immutable, so withoutNote(...) and withPetReplaced(...) return new objects instead of changing p and c.
  4. d calls Model#setClient(...) once to swap in the updated client, then returns a CommandResult.

All checks happen before the Model is changed, so a failed command never leaves partly updated data:

Design consideration: how a user removes a note

  • Alternative 1 (current choice): a separate delnote command, with nt/ required in note.
    • Pros: each command does one thing, so a note can never be removed by accident, and the error messages are specific.
    • Cons: one more command for users to learn.
  • Alternative 2: note with an empty or missing nt/ removes the note.
    • Pros: one command covers adding, replacing and removing.
    • Cons: a typo such as a forgotten nt/ silently deletes a note, and "a note with no text" is confusing.

Appendix: Requirements

Product scope

Target user profile:

  • is an independent mobile pet groomer
  • has a need to manage a significant number of client contacts, their pets and appointments
  • prefers desktop apps over other types of applications
  • can type fast
  • prefers typing to mouse interactions
  • is reasonably comfortable using CLI apps

Value proposition: Manage client contacts, appointments and related pet information faster than with a typical mouse-driven GUI application.

These stories include implemented features and desired enhancements; priority does not indicate implementation status. The current commands are listed in the User Guide. Date-based appointment filtering, searching note contents, filtering by safety information and filtering by tags are not implemented. Tags categorise clients only. Non-Functional Requirements

  1. PawPals should work on any mainstream OS as long as it has Java 25 or above installed.
  2. For a dataset of up to 100 clients and their associated pet and appointment records, common commands such as list and find should complete and update the displayed results within 1 second.
  3. All core PawPals workflows should be completable using keyboard input without requiring mouse interaction.
  4. Client, pet, and appointment data that has been successfully saved should remain intact and available after PawPals is closed and subsequently relaunched.
  5. PawPals should support at least 100 clients and their associated pet and appointment records.

Glossary

  • Client: A customer of the pet grooming business whose contact and home address information is stored in PawPals. A client may have zero or more pets.
  • Pet: An animal belonging to a client whose grooming-related information is managed in PawPals.
  • Appointment: A grooming visit associated with a client that remains active until completed or cancelled. Its start may be in the past, present or future.
  • Grooming session: A completed grooming service whose details and notes are recorded for future reference.
  • Safety information: Information about a pet that may affect how it should be handled or groomed, such as temperament, behavioural concerns, or grooming-related sensitivities.
  • Client index: A positive integer identifying a client in the currently displayed client list. It is used by commands that require the user to specify a particular client.
  • Mainstream OS: Windows, macOS, or Linux.
